# 《A2A 传文件方案》自评审

> 对 `docs/a2a-file-transfer-plan.md` 与附带的 `.openthree/functions/a2a_file_link.py`
> 先自己反驳一遍。评审时间是写完文档之后、交付之前。

## 一、结论先行

- **骨架与项目哲学一致**：不硬编码判断（明确反对「正文标记法」）、单一真源
  （状态挂 `KERNEL.state`）、不预设流程（工具只登记，不指挥）。
- **两处 P0 都已在交付前修掉**，且都不是自评审看出来的，是**实测**逼出来的：
  1. 工具第一版声称「重载后链接与端口一起消失」—— **这是假话**：`reload_functions()`
     只重新 exec 模块，已经绑好的 socket 与服务线程还在跑。照原写法，重载后
     「旧服务还在、新模块看不见它」，新发布会撞 `EADDRINUSE`。
  2. 中文文件名直接崩：`Content-Disposition` 按 latin-1 严格编码，非 ASCII 名抛
     `UnicodeEncodeError`，**整个响应被掐断**（实测报错原文见下）。现在 ASCII 一份
     + `filename*=UTF-8''` 一份。
- **P1 三条、P2 五条**记在下面，都不影响「R1 能用」这个结论，但会影响你怎么用它。

## 二、设计哲学八问

| # | 问 | 落在哪 |
|---|---|---|
| 1 | **道**（无硬编码智能） | 方案里没有任何「按内容决定怎么办」。R3 的三条缝里，专门把「答案里出现 `[[file:路径]]` 就解析」判为**反对**——那是把判断写进正则。工具也不判断「该不该发」，只登记路径。 |
| 2 | **一**（可写 · 可回滚） | 本方案不开新的 system 写入通道。唯一进 system 的是工具自带的 291 字符 `__system_prompts__`，走的是既有的 `build_attached_block`，改它等于改那个文件，可读可回滚。 |
| 3 | **二**（磁盘即真源 / 单一真源） | 工具的链接表只有一份，挂 `KERNEL.state["a2a_file_link"]`，处理器从 `server.links` 取，**不读模块全局**。这是 P0-1 的修法，也是「同一件事别写两处」。 |
| 4 | **三**（循环不预设） | 不给模型规定「先 publish 再回答」。它也可以选择「这个文件不该发」而直接说明理由。 |
| 5 | **万物**（自造） | R3 的设计让「发文件」成为模型可以自己调用的能力（`deliver_file`），而不是内核替它猜。R1 是同一件事的零改动版本。 |
| 6 | **极简** | 工具只有三个函数、一条路由（`/f/<token>`）、一个参数组。方案明确写「能用 R0 就别用 R1」。 |
| 7 | **成本** | R2 的 token 成本算过（≈ 3 字符/token，成倍膨胀）；R1 的成本是**常驻 system 291 字符** + 一个监听端口。两者都写了。 |
| 8 | **诚实** | 「17 项 / 21 项实测通过」「字节完全一致」都有脚本可复跑；所有 token 数字都标了「估算」而不是实测。 |

## 四、缺陷清单

### P0（已修）

- **P0-1 重载后状态分叉。** 初稿把链接表放模块全局；`reload_functions()` 后旧服务
  线程仍用旧表，新模块拿空表 → 旧链接仍可取但 `list_links` 看不见、同端口再发布撞
  `EADDRINUSE`。**改法**：状态挂 `KERNEL.state`，处理器改从 `self.server.links` 取。
  **实测**：`filelink_reload.py` 4 项全通过（同端口 52896、旧链接仍 200、`list_links`
  同时看得见 a.txt 与 b.txt）。
- **P0-2 中文文件名掐断响应。** `send_header` 用 latin-1 严格编码，
  `"报告 2026.bin"` 抛 `UnicodeEncodeError`，客户端收到 `RemoteDisconnected`。
  **改法**：`_safe_name()` 只留 ASCII（`filename="…"`），真名走
  `filename*=UTF-8''…`。**实测**：`filename="__ 2026.bin"; filename*=UTF-8''%E6%8A%A5…`。

### P1（答辩时站不住）

- **P1-1 R1 的隐含前提被埋在「代价」列里。** 若对端是公网 registry 发现我们的 agent，
  它多半在另一个网络 —— R1 直接不成立。已在 §3 表格**下面**补一段显式前提：先回答
  「对端在哪」，再谈路线。
- **P1-2 R3 推荐方案 (a) 依赖「全局 outbox 不串台」，而我只核到桥自己串行。**
  `-i` 交互入口与频道桥是否共享同一把 run 锁，本方案**没有验证**。这是 R3 动手前的
  第一件事：若不互斥，(a) 就得改成「按 run 分槽」。
- **P1-3 同一个文件重复发送会不断产生新 token。** `list_links` 不回显 URL（安全上
  是对的），所以「对端没收到，我再贴一次」只能重新 `publish_file`。已在 §4.6 写明。

### P2（措辞与顺带）

- `_safe_name` 会把中文名换成 `_`，老客户端保存的成本是 `__ 2026.bin`；只有认
  `filename*` 的客户端能拿到真名。已在 §4.4 用实测原文说明。
- `read_bytes()` 全量进内存，且 sha256 又读一遍；并发 N 个 ≈ N 份文件大小。已写进边界。
- 同一个 `publish_file` 若先 `port=0` 再 `port=8123`，会起**第二台**服务（键是
  `(host, port)` 的原值）。不是 bug，但值得知道。
- 没有 HEAD / Range，大文件不支持断点续传。已写。
- 把这份工具**同时**复制进两个 profile，两份 `__system_prompts__` 都会进 system
  （上一轮 profile 指南记录的既有行为）。已在 §4.1 提醒只放一处。

## 五、待人类拍板（我不替他定）

1. 对端在哪（同机 / 局域网 / 公网）—— 决定 R1 是否可行、`host` 与 `base_url` 填什么。
2. 文件多大、取几次 —— 决定 R0 / R1 / R3。
3. 要不要走 R3（改 5 个文件、动卡片与频道契约）—— 你不点头，我不碰内核。
