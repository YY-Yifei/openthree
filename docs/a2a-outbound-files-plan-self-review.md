# 自评审：A2A 出站文件支持方案

> 评审对象：`docs/a2a-outbound-files-plan.md`
> 时间：2026-11-12 · 方法：先自己反驳一遍，再对着源码核事实

## 0. 结论

骨架与项目哲学一致：改动的**能力**部分落在频道层，「附不附、附哪个」留给模型，安全策略留在频道层。
缺陷分三层：

- **第一层（核心假设）**：第一稿默认开启出站文件。**这是错的** —— 卡片会因此撒谎（声明了
  `application/octet-stream` 却可能永远送不出 file part），且它默认把一份本机文件读取能力
  挂到一个**无鉴权**的端点上。已改成「默认关，`outbound_roots` 非空才开，卡片跟着开」；
  第二轮人拍板默认开启后又反过来读（§8.1）。
- **第二层（边缘机制）**：「当前回合」用固定键存会串台；「对端一定能拿到」是句不诚实的
  保证；同一份字节在「响应 + 回调」里会走两遍。前两条已改，第三条写进体积账。
- **第三层（落点，第三轮）**：前两稿把 `attach_file` 定成「用户自己装一个 function 文件」。
  人明确否掉了：要「发新包后，别人 A2A 模式启，自然具备」。于是它变成**内置工具 + 注册期门控**，
  代价是**必须动内核三个文件**（`builtins.py` / `runtime.py` / `cli.py`）—— 「内核零改动」
  这条边界由人主动放弃，不是我自己放宽的。详见 §9。

仍留 3 条 P1（1 条需实测、2 条需人拍板），列在 §5。

## 1. 八问

1. **道（无硬编码智能）**：`_outbound_file_parts()` 只做两件事 —— 安全判定与格式转换，
   **不决定发什么**。被拒的文件不修改模型答案，只追加一句原因。方案明确拒绝「自动附上本轮
   生成的所有文件」那种魔法（那是替模型做判断）。
   有一处用到了 `if`，需要说清它不是智能：`if is_notice: files = []` —— 判的是桥留下的
   **带外标记** `msg.raw["notice"]`，不是文本前缀（`send_text:1506-1510` 的注释解释了为什么
   不能按前缀判）。**通过**。
2. **一（可写 · 可回滚）**：本方案不往 system 里写任何东西。`attach_file` 的说明走
   **工具 docstring → description**（内置工具没有 `__system_prompts__` 通道，那是 function
   文件的机制，见 `registry.py:36-39`）—— 于是它**不进** system，也不产生「谁改过这段提示词」
   的追溯问题，比原设计更干净。原文曾写「走 `__system_prompts__`（profile 附随提示词）」，
   那是第二稿的用户态路线，第三轮已废。**通过**。
3. **二（磁盘即真源）**：默认值只写 `a2a.py` 模块常量一处，`config.py` 的 `Field` 只写 hint
   （`config.py:101-102` 明写这条规矩）。方案 §6 必须遵守 —— 第一版没写，现在明确。**通过**。
4. **三（循环不预设）**：工具不排顺序、不要求先做什么。**通过**。
5. **万物（自造）**：`attach_file` 是**用户态**工具，不是内置 —— 先证明有人用，再谈进内核
   （`docs/` 里已有「没被用过的兼容层宁可不要」的先例）。代价是每个用户要自己装，写在 §9 阶段 3。
   **通过**。
6. **极简**：新增 4 个常量 + 1 个配置项 + 1 个字段 + 1 个工具。自问能减哪个：
   `MAX_OUTBOUND_TOTAL_BYTES` 与 `MAX_OUTBOUND_FILES` 只能拦「多而小」，而 4 个 2 MiB 是
   单文件闸的四倍 —— 不能减。**通过**。
7. **成本**：system 字节不变（附随提示词是常量，不随输入变）；`attachments` 只在
   `InboundMessage` 上，不进模型上下文。**通过**。
8. **诚实**：第一稿写「对端一定能拿到」—— 不诚实：对端若只读 `text` part，它仍只看到字。
   已改成「不依赖网络可达性」。另有两处「自动 / 不影响」类的措辞被删或加了限定（见 §5）。
   **基本通过，留一条 P1 实测项**。

## 4. 我改了自己哪些话（都是错的）

1. 「默认 `<workspace>/assets`、`<workspace>/tmp`」→ 改成 **默认空**（功能关闭）。

## 5. 缺陷分级（按「实现出来会不会错」）

**P0（实现出来是错的）**

- **P0-1 默认开启会让卡片撒谎**。判据 → 改法：`defaultOutputModes` 必须与真实能力同源
  （既有判据 `a2a.py:524-526`「卡片不撒谎」）→ 由 `outbound_roots` 是否非空决定。
- **P0-2 无鉴权端点 + 任意路径 = 远程文件读取通道**。判据 → 改法：根白名单 + 硬黑名单 +
  三道上限 + 名字消毒（§4）。**这条是第一稿完全没有的**，也是最贵的一条。
- **P0-3 「当前回合」用固定键会串台**。判据 → 改法：按线程 id 存。

**P1（答辩时站不住）**

- **P1-1** 「工具与 `rt.run` 同线程」未经实测 → 实现时先加一条断言 / 一条测试
  （在工具里断言 `threading.get_ident()` 与 `rt.run` 调用线程相同），再谈这条契约成立。
- **P1-2** 卡片改 outputModes 对严格客户端的影响未知 → 实现时提供一个开关的负向验证：
  关掉 `outbound_roots` 时卡片必须与今天**逐字相同**（`["text/plain"]`），保证默认零行为变化。
- **P1-3** 「开了开关却没装 `attach_file`」→ 模型想附也附不上，而卡片已声明。
  判据 → 改法：§9 写明「开启前先装工具」，并在文档里给出开启顺序（装工具 → 配根 → 重启频道）。

**P2（措辞与顺带）**

  不对称是有理由的（出站没有请求体硬闸，只有 5s 回调超时），方案 §5 已解释。

## 8. 第二轮：人拍板「默认开 + 20 MiB」之后，方案里哪些账要重算

人的两句话改了两个默认值，而**这两个默认值各自把一条 P1 顶成 P0**。

### 8.1 上一轮的 P0-1 现在要反过来读

上一轮 P0-1 写的是「默认开启会让卡片撒谎」。人已经决定默认开启，所以那条 P0 **不是被否决，
而是被满足了**：解法仍然是「卡片与真实能力同源」—— 现在同源的方向是「默认就声明能回文件」，
`outbound_roots: []` 才是那个不一致的方向（关了还声明 = 撒谎）。
两处措辞已按这个方向改（§4 闸 0、§6 表格）。**判据没变，方向变了。**

### 8.2 新的 P0（都是决策变更的算术后果）

- **P0-4 20 MiB × `TASK_LIMIT = 200` = 5.4 GB**。判据：`a2a.py:102` 的任务表常驻内存，
  每条 task 都可能带一份 27 MB base64 → 不改就是 OOM 定时炸弹。改法：加 `MAX_TASK_FILE_BYTES = 256 MiB`，
  超了把**最旧** task 的 file part 降级成 `[文件已过期：name]` 文本。降级写在协议里，不静默丢。
  （上一轮没这条，因为它按 2 MiB 算 = 540 MB，还能装作「可接受」。20 MiB 把这个假设打穿了。）
- **P0-5 回调投递必然超时**。判据：`PUSH_TIMEOUT = 5.0`（`:108`）+ 整份 Task POST（`:1631`），
  公网 20 Mbps 上行传 27 MB 要 11 秒。改法：**有附件时跳过回调**（或另行决定延长超时），
  并把这条写进 `--help` 与 §11。上一轮把它当「提醒一句双倍带宽」，20 MiB 之后它是功能性的。

### 8.3 新的 P1

- **P1-4 默认开 = 默认有一条远程读文件通道**。靠 `DEFAULT_HOST = "127.0.0.1"`（`:65`）兜着，
  但跨机场景人一定会改 `-A2A-host 0.0.0.0`。判据 → 改法：把警告放在 `-A2A-host` 的 help 文本
  旁边（§4 闸 0 已写），并在 §11 说明默认根是工作区、需要收窄就写 `assets,tmp`。
- **P1-5 对端也是 openthree 时 20 MiB 送不进去**。判据：对端入站硬闸 `MAX_BODY_BYTES = 8 MiB`
  （`a2a.py:87`、`:744-746`）→ 27 MB POST 直接 413。改法：文档点名这条，并把它作为阶段 2（URI 路由）
  的第二个理由；不擅自改对端常量。
- **P1-6 上一轮 P1-1（工具与 `rt.run` 同线程）从「无证据」升级为「代码可证、仍未实测」**。
  证据：`bridge.ask` 在 `with self._run_lock:` 里同步调 `self.rt.run(...)`（`bridge.py:114-124`），
  而工具是在 `agent.py:1021-1024` 里被**直接调用**（`tool.func(**call_args)`），没有线程池、没有
  `asyncio.to_thread`。所以「同一线程」成立，但仍是**读代码得出的**，不是跑出来的 —— 实现时补一条
  断言（`attach_file` 里断言 `threading.get_ident()` 与桥发布时相同），把它变成回归测试。

### 8.4 修正的旧话

- 上一轮自评 P2-3 说「2 MiB 与入站 8 MiB 不对称是有理由的」。20 MiB 之后**这句话失效**：
  出站单文件已经大于入站整条请求的上限，不对称反而成了「对端收不下」的病（P1-5）。已改 §5。
- 上一轮自评 P1-3 说「开启前先装工具」。默认开启之后顺序反了：**工具是可选件，频道层能力才是必需件**
  —— 没装工具只是模型不能主动附，不会骗人（§3.4.6 的降级表）。已在 §3.4.6 说清。
  **第三轮之后这条再变一次**：工具不再是「可选件」，它随包发布并在 A2A 进程自动注册（§9）。

### 8.5 `attach_file` 挂载这件事，本轮新核实的四条（都有代码位置）

1. `Kernel.state` 确实存在，注释就是「给用户 function 自由使用的草稿纸」（`kernel.py:20`）；
   `KERNEL = Kernel()` 是模块级单例（`kernel.py:29`）。
2. 注入路径：`agent.py:1021-1022` `if tool.needs_kernel: call_args["kernel"] = KERNEL`
   —— 工具拿到的与桥拿到的是**同一个对象**。
3. `manager` 只有**一条 bridge**（`manager.py:121` `self.bridge.submit(msg, channel.send_text)`），
   所有频道共用它 → 同一把 `_run_lock` → 同进程同一时刻只有一条 ReAct。
4. `reply` 是绑定方法，`getattr(reply, "__self__", None)` 就能拿回频道实例 —— 于是
   「这个频道支不支持出站文件」可以问频道自己（`supports_files`），而 `submit()` 签名不用动。

### 8.6 本轮仍然没做的

- 没有写一行源码、没有跑 pytest（方案阶段）；
- `attach_file` 的源码写在文档里（§3.4.5），**没有落盘**到包里 —— 因为频道层还没实现，
  装上它只会说「这次答复发不出文件」，等于给模型一个假工具（**第三轮改为内置**，见 §9）；
- 没有实测 20 MiB 的端到端（要等阶段 1 落地）。

## 9. 第三轮：人否掉了落点 —— 「要发版即得，不是让用户自己装」

人的原话：「不对吧，我是期望我们发新的包后，别人A2A模式启，自然具备这个能力，应该还是A2A时才加这个能力」。

### 9.1 我错在哪

前两稿的 §3.4 都在回答「这个 function 文件放哪儿」：项目 / profile / 用户目录，
再补一句「`-profile` 挂上就带着」。那是在**回答一个不该问的问题** —— 它把

前两稿的答案是「什么都不会发生」，那不是他要的。

正确的落点是 `decide` 那条路（`builtins.py:2928-2940` 的「常驻集 + 条件集」）：
内置模块 + 注册期按条件挂载。这是**现成机制**，不是新发明 —— 我前两稿没看见它，
是因为一直在「用户态」这个框里找答案。

### 9.2 三笔必须付的代价（都已写进主文档）

1. **「内核零改动」作废**。内置工具必然动 `builtins.py` / `runtime.py` / `cli.py` 各几行
   （`channels/manager.py` 加一个 `declares_a2a`）。这条边界是**人主动放弃的**，不是我自己

2. **纪律不能再走 `__system_prompts__`**。那是 function 文件的机制（`registry.py:36-39`、

   description 就在眼前，比 system 尾部的附随提示词更贴切。代价是它计入工具 schema。
3. **门控信号要算准**（下面 §9.4 的 P0-7 就是第一版没算准）。

   `:105` 才注册工具。
3. `is_registrable` 第三档按 `__module__` 过滤（`tool.py:230`）→ 把 `attach_file` import 进
   `builtins.py` **不会**让 `python -m openthree.builtins --help` 多出一个子命令。
4. `openthree/channels/` 全目录**不 import** `runtime`（regex 检索 0 命中）——
   所以延迟 import 的理由**不是**绕循环；真实理由是别让内核模块加载期就依赖频道层。
   我第一版把这句理由写成「避免成环」，是错的，已改。
5. `a2a` 的 `ChannelSpec` 一条 required 都没有（`channels/config.py:100-101` 注释明说）
   → `is_ready()` 恒为真，**不能**拿 `has_configured_channels` 的 `ready()` 判据复用。
6. 内置工具的 `source_distance` 最远（`registry.py:181` 注释：「任何同名的外部工具都顶得掉它」）
   → 用户写同名 `attach_file` 会赢，这是既有规则，不开例外。

### 9.4 缺陷分级（第三轮新增）

- **P0-7（实现就会错，已修）**：门控第一版只判 `args.a2a` 与 `--no-channels`，漏了
  `-u` 升级模式 —— 它走 `_interactive(..., no_channels=True, ...)`（`cli.py:419-422`）
  **在调用点硬编码**关频道，而 `args.no_channels` 仍是 `False`。判据 → 改法：三态里加
  `not args.upgrade`。这条同时暴露一个更普遍的事实：**「关频道」有两个真源**。
- **P0-8（设计意图会被误读，已修）**：第二稿让 `attach_file` 依赖 `__system_prompts__`。
  改成内置后**那个通道根本不存在**，若不改，四条纪律会静默消失（不是报错，是没人写进去）。
  判据 → 改法：纪律进 docstring，并在主文档 §3.4.5 说明为什么这反而更贴切。
- **P0-9（我自己的第一版就是错的，已修）**：门控若只判 `channels.yaml`，**单次任务**
  （`openthree "任务"`，`cli.py:433-468` 全程不加载频道）会在有 a2a 声明的工作区里
  注册一个永远用不上的工具 —— 而单次任务是 CLI 的主力用法。
- **P1-7（不修，说明了理由）**：门控判「会起」而非「已起」。`--only wechat` 时工具在、
  却没有承载者 → 只会导致「调用时老实说发不出去」。要精确就得把注册推迟到 manager 装配后，
  那会让工具集在进程中途变化、system 前缀每步都变，代价更大。
- **P1-8（要写进 docstring）**：嵌入者（`channels/__init__.py:12-20` 那条演示路径）必须
  显式 `Runtime(project_dir, a2a=True)` —— 因为 `None` 只读磁盘，读不到他们内存里注入的频道配置。
- **P1-9（未验证，实现时必测）**：`declares_a2a()` 读的是磁盘上的 channels.yaml，
  而 `-A2A` 的注入项只活在内存。两者在 `apply_extra()`（`manager.py:208-230`）里才合并。
  所以「磁盘说没有、命令行说有」时，靠 cli 的 `a2a_flag=True` 兜住 —— 但**没有实测**过
  这条合并路径对门控的影响。
