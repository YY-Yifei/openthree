# 快跑：把时间交还给模型

> 目标：让「短、平、快」的活真的快起来，而**不削掉模型的任何一只手**。
>
> 基线数字全部来自本仓库 `.openthree/logs/` 的 19 个真实任务（1264 次模型往返、
> 1700 次工具调用），可复算。
>
> **状态**：支柱 A 的第一项（静态前缀 / 处境尾消息）已落地并实测，
> 见 §3.2 与 §6.1。其余各项仍是方案。

---

## 一、一句话结论

**内核只该为三分之一的时间负责，剩下的三分之二在模型自己的思考里。**

所以快起来只有两条路，缺一不可：

1. **内核把自己那一份浪费清零** —— 不是砍能力，是把「每步都在重发、且每次都没被缓存」的那些字节修好。
2. **把时间变成模型手里一把看得见、算得清的尺子** —— 它自己决定哪儿想深、哪儿想浅、
   什么时候收口。内核不替它判断「这个任务只值 12 步」。

`-fast` 因此不是「降级模式」，而是**一份时间契约**：人类说「这一活我只要两分钟」，
模型在这个期限内全权调度。工具一个不少，提示词一个字不减。

## 二、先看时间到底花在哪

### 2.1 总量

| 指标 | 数值 |
|---|---|
| 任务数 | 19 |
| 模型往返总数 | 1181（中位任务 **62 次**，最多 158） |
| 工具调用总数 | 1700 |
| 模型墙钟合计 | **14077 s**（3.9 小时） |
| 工具墙钟合计 | 5480 s |
| prompt 总量 | 74.2 M tok |
| completion 总量 | 1215 k tok |
| **prompt 命中缓存** | **3.07 M tok = 4.13 %** |

中位任务：**62 步 / 模型 819 s + 工具 386 s = 1205 s**。

### 2.2 用固定效应回归拆开这 14077 秒

`ms = a + b·未缓存prompt + c·completion`，并对 19 个会话各给一个截距
（消除「不同任务本身难度不同」造成的偏差），R² = 0.865：

| 成分 | 系数 | 合计 | 占比 |
|---|---|---|---|
| 每次往返的固定开销 | 1.15 s / 次 | 1349 s | **9.9 %** |
| 未缓存的 prompt | 0.0444 ms / tok | 3113 s | **22.8 %** |
| completion（模型生成） | 7.25 ms / tok | 8465 s | **61.9 %** |
| 会话间差异（任务本身） | — | 756 s | 5.4 % |

**这张表是整个方案的起点**：内核能动手的是前两项，合计 **32.7 %**。
另外 **61.9 % 是模型自己在想** —— 内核没有任何正当理由去砍它，
能决定「想多少」的只有模型自己。

而 completion 里 **69.9 % 是 reasoning token**（1123 次调用实测）。
也就是说：这 61.9 % 里，绝大部分是模型真的在推理，不是废话。

> ⚠️ **这张表的第二行只在「未缓存」的意义上成立，不能拿它去算「命中缓存能省多少」。**
> 回归是在**全程几乎不命中**的数据上拟合出来的（基线命中率 4 %），它测的是
> 「prompt 变长带来的边际成本」。而缓存命中省下的是另一件事，实测边际收益
> **远低于**这个系数：
>
> | prompt 规模 | 冷 → 热 省下 | 每 1000 命中 tok |
> |---|---|---|
> | ~8 k | 313 ms | 84 ms |
> | ~28 k | 306 ms | 23 ms |
> | ~41 k | 481 ms | 12 ms |
> | **~105 k（真实任务规模）** | **840 ms（19 %）** | **8 ms** |
>
> 按 0.0444 ms/tok 线性外推，105 k 该省 4643 ms —— 实测只有 840 ms，
> **高估 5.5 倍**。所以本方案对「修缓存值多少」的承诺按本表最后一行为准，
> 不按回归系数外推。省 19 % 仍然是很大的一笔，但它不是 22.8 % 那么多。

### 2.3 每步到底多贵

单次往返的模型耗时在会话之间相差 6.5 倍：最省的 **4.18 s/步**，
最费的 **27.02 s/步**。原因是它同时取决于两件互不相关的事：
历史有多长（prompt）与这一次想了多少（completion）。工具耗时还会在此之上
再叠一层（有的会话工具占了 59 % 的墙钟）。

**这条事实否定了「用步数当代理」的做法**：同样是 12 步，可能只花 45 秒，
也可能花 5 分钟。步数不是时间的代理量。

### 2.4 这些开销里，哪一部分是内核的错

| 现象 | 实测 | 判定 |
|---|---|---|
| prompt 命中率 4.13 % | 3.07M / 74.2M | **内核的错**（见 2.5） |
| 工具清单发了两遍 | `digest` 1485 tok + `tools` schema 10456 tok，每步都发 | 内核算计不周 |
| 同批多调用串行执行 | 470 个 step 含 ≥2 调用，串行 | 内核的错（收益小，0.7 %） |
| 工具输出 13 % 被截断 | 219 / 1686 条 ≥ 3900 字符 | 半是内核的错（截断提示不可操作） |
| 62 次往返 | 中位任务 | **不是错** —— 任务本身就这么深 |
| completion 899 tok/步 | 中位任务 | **不是错** —— 那是模型的思考 |

### 2.5 缓存只有 4.13 %，是结构问题，不是模型慢

同一份请求**重发一次**时，服务端给出的缓存命中是 **99.86 %**
（`cached=54400 / prompt=54474`，某次重试）。这说明两件事：

1. 服务端确实做前缀缓存，而且粒度很细；
2. 我们的请求前缀**每一步都在变**，所以几乎全 miss。

原因在 `prompt.py`：`build_messages` 把系统提示词与整个处境块**拼进同一条 system 消息**——

```python
{"role": "system", "content": f"{system_prompt}\n\n{runtime}"}   # prompt.py:275
```

而 `runtime` 的第一行就是 `- 当前时间：…`。于是这条消息的**前缀**是稳定的
（`system_prompt`，2812 tok），但它**后面每一个字节每步都变**。
缓存只能保住那条消息里稳定的一小段，再往后全部作废。

### 2.5.1 缓存恰好停在系统提示词结束的地方

```
20261020-090845-3076-6  众数 cached=3072（73 次调用里出现 59 次）
20261021-090837-32508-1  众数 cached=3072（120 次调用里出现 86 次）
20261019-161248-3076-2  众数 cached=3072（62 次调用里出现 30 次）
```

而当前 `system-prompts.md` 是 5624 字符 ≈ **2812 tok**。

> **命中部分 = 系统提示词恰好那么大。**
> 也就是说：缓存恰好停在「系统提示词结束」那一行，从它之后的每一个字节
> （处境块、工具清单 1485 tok、工具 schema 10456 tok）**统统没命中**。
>
> 这不是「cache 命中率低」，是**前缀从第 2812 个 token 起就断了**。

### 2.5.2 首调那 15687 tok 是什么

首调时 history 里只有一条用户任务，所以 prompt 几乎全是「内核自己的东西」：

| 组成 | 字符 | ≈ tok |
|---|---|---|
| 工具 JSON schema（35 个，`tools=[…]`） | 20912 | **10456** |
| 系统提示词 `system-prompts.md` | 5624 | 2812 |
| 工具清单 `digest`（与上面同一批，讲第二遍） | 2970 | 1485 |
| 计划 + 长期记忆 + 演化史 + 业务任务 | — | ~900 |
| **合计** | | **≈ 15653**（实测中位 15687） |

**工具相关的字节占了首调的 76 %**（10456 + 1485），而这份内容从第 1 步到第 158 步
**一个字都没变过**。它本该 100 % 命中缓存，实际命中 2048 tok。

这就是为什么「砍工具省 token」这个直觉在这里是错的：那 11941 tok 是**固定的、
可缓存的**。该修的是缓存，不是删工具 —— 删掉工具省下的是每步约 0.19 s，
修好缓存省下的是每步约 0.84 s（真实规模实测，见 §2.2），
而且一个不损失能力，一个要损失。

### 2.6 历史任务有多深（决定 `-fast` 该承诺什么）

把 19 个历史任务按「如果给时间预算，会走到第几步」回放：

| 时间预算 | 能在预算内 finish 的任务 |
|---|---|
| 60 s | 0 / 19 |
| 120 s | 1 / 19 |
| 180 s | 2 / 19 |

**这条数据必须写在方案最前面**：历史上几乎没有任务能在 120 秒内做完。
所以 `-fast` 的正确承诺**不是**「让重活变快」，而是：

> 「这是一次有期限的快跑。到点交付一个诚实的阶段结论 —— 做完了什么、
> 没做完什么、下一步从哪接。」

把「变快」误解成「把 1205 秒的任务压到 60 秒」，只会得到一句话都说不全的半成品。

## 三、设计

### 3.1 支柱 A：内核自己的浪费清零（对所有模式生效）

**A1. 让请求前缀真正稳定 —— system 完全静态，每步变化的一切挪到末尾。**

```
messages = [
    {"role": "system", "content": STATIC},     ← 系统提示词 + 工具清单 + 身份，逐字节不变
    ...history,                                 ← 只追加，不改写
    {"role": "user", "content": 处境},          ← 唯一每步变化的部分，不进 history
]
```

`STATIC` 只含三类东西：`.openthree/prompts/system-prompts.md` 原文、工具清单
（`digest`）、以及模型自己起的名字。三者都只在「模型主动改它们」时才变 ——
那时**本来就该 miss 一次**，然后重新稳定。

「处境」（时间 / 第几步 / 上下文用量 / 运行边界 / 上次行动）每步重新生成，
作为**最后一条消息**附上，**不写入 history**。

注意「计划 / 长期记忆 / 演化史」归在 `STATIC` 一侧，而不是「处境」一侧：
它们虽然也每步重读，但**只在模型自己写它们时才变**。把它们放进末尾那条，
等于每步都把 641 + 953 + 287 tok 当成「变化段」——而它们的常态是不变的。
判据是把它们分开的那条：**「内核自己会不会让它每步都变」**，不是「它读的是不是文件」。

这样前缀 = `STATIC + history`，而 history 只追加 → 除最后一条外全部可命中。

> **已实施并实测**（2026-10-21，`openthree/prompt.py`）。五组真实 API 对照
> （~36k tok 前缀，只有变化位置不同）确认服务端就是前缀匹配，断点精确落在
> 第一个不同的字节上：
>
> | 变化段位置 | 命中率 |
> |---|---|
> | system 开头（第 3 行） | 0.0 % |
> | system 中部（今天的行为） | 51.0 % |
> | system 末尾 | 99.8 % |
> | **末尾一条 user 消息** | **99.8 %** |
>
> 另外确认 `tools` 也参与缓存，但序列化顺序是 `system → tools → messages`，
> 所以「变化段挪到 system 末尾」不够（仍会连带废掉 tools，实测 65 %）——
> 只有挪到 messages 末尾才完整。
>
> 端到端实测（真实 Agent + 真实 API，5 次任务）：命中率 **66.4 % / 76.9 % /
> 81.4 % / 85.2 % / 87.1 %**，对比历史基线 **4.06 %**。首步仍是冷启动（必需），
> 之后稳定在 85~95 %；低于 80 % 的那次是短任务（5 步，冷启动占比大）加上
> 服务端缓存抖动（同一请求重发的命中值会在 2048 / 2944 / 整段之间跳）。
> 命中的**下限由服务端抖动决定，不是结构问题** —— 但这也说明不宜承诺
> 「稳定 90 %+」，按 80 % 左右做规划才诚实。

**A2. 去掉重复的工具清单（可选，放在 A1 验证之后）**

`digest` 与 `tools` schema 讲的是同一批工具（1485 tok vs 10456 tok）。
A1 修好后这部分基本走缓存，代价接近于 0，所以**不为了省 token 去删它** ——
它是模型「一眼看清自己有什么手」的目录。只有当首调延迟成为问题时，
才把它降级为「只列名字」。

**A3. 同批工具调用并行执行**

470 个 step 里含 ≥2 个调用，串行执行。并行能省 **134 s**（工具墙钟的 2.4 %，
端到端 0.7 %）。收益小，但它是**零风险的**：调用之间本来就互不影响
（模型把它们放进同一批，就是声明了它们互不依赖）。

顺带的价值更大：它让「批量调用」这件事**真的划算**，从而与支柱 C 的
「一次把要看的都看了」形成闭环。

**A4. 截断提示改成可操作的**

13 % 的工具输出撞到 4000 字符上限。现有提示只说「可用 read_file 读取」，
模型往往直接重读一遍 → 又一次往返。改成给出**下一步的精确参数**：

```
... [已截断：共 9821 字符，这里是前 4000。继续读用
     read_file(path="…", offset=…, limit=…)；或缩小检索范围]
```

这不是新功能，是把已经知道的信息说清楚。

### 3.2 支柱 B：时间成为第六个边界

现有的五个旋钮（步数 / 轮数 / max_tokens / 工具结果宽度 / 温度）都是
「看得见 + 改得动 + 显式即锁定」。**时间完全同构**，所以不发明新机制：

| 项 | 值 |
|---|---|
| 旋钮名 | `time_budget`（秒，0 = 不限） |
| 落点 | `.openthree/limits.json`（与其余五个同一个文件） |
| 默认 | **0（不限）** —— 不传就是今天的完全一样的行为 |
| 显式 `--time-budget N` | 锁定（模型改不动，与 `-n 30` 同语义） |
| 模型自管 | `set_limits(time_budget=…)` |
| 读数 | `limits_usage` 多一行；处境里每步一行 |

**为什么是时间而不是步数**（§2.3 已回答：步数不是时间的代理）。
一条 `pytest` 就能吃掉 20 步的预算，一次 hi 只要 4 秒 —— 只有时间能表达
「用户到底在等多久」。

**期限怎么算**：从本轮开始计时，包含模型往返与工具执行 —— 那正是用户在等的。
轮与轮之间（`--auto` 接力）各自重置，处境里会同时显示「本轮预算」与「本场已用」。

**软着陆，不是铡刀**：

1. 内核维护本场实测的「每步耗时」滑动均值（EMA），于是能把剩余时间**换算成步数**
   说给模型听：`剩余 38 s ≈ 3 步（按本场实测 12 s/步）`。
2. 剩余时间 < 1 个实测步长时，处境里插一句：`预算将尽：再走一步就会超时，请收口`。
3. 剩余时间 ≤ 0 时，**允许最后一整步**用于 `finish`（与「`finish` 自己也要占一步」
   同一个道理），并在结论里注明哪些没做完。
4. 用完仍没有 `finish`：如实结束，`status=unfinished`、退出码非 0，
   结论里写清「预算用尽，停在第 N 步」。

**唯一的新增状态是 `limits.json` 里多一个键**，且只有模型自己写它才会出现；
`-fast` 传的是显式参数，**不落盘**（一次快跑不该改变之后所有任务的节奏）。

### 3.3 支柱 C：快是模型的选择，内核只负责让它算得清

内核做不了「想得少而想得对」，那只有模型能做。内核能做的是三件事：

**C1. 把代价摆在眼前**（每步，处境里一行）：

```
- 配速：快跑 · 预算 120 s / 本轮已用 74 s / 剩 46 s ≈ 3 步（本场实测 12 s/步）
```

**C2. 把「怎么快」讲清楚**（只在快跑契约生效时追加，是提示不是硬编码）：

```
# 这一趟是快跑（预算 120 s）

- 一次把要看的都看了：多个 read_file / search_files 放进同一批，不要一步一个。
- 先给小的验证，再决定要不要跑全量。一条 400 s 的命令会吃掉全部预算。
- 拿到够用的结论就收口：用 finish 写清「做完了什么 / 没做完什么 / 下一步从哪接」。
- 觉得这个期限根本做不完，就**先说出来**（一行说明 + 需要多少时间），
  不要闷头做到超时。
```

**C3. 让它能自己按下加速键**：不传 `--time-budget` 时预算是 0（不限），
模型若判断「这活该快点」，可以自己 `set_limits(time_budget=120)` —— 与它现在
自己调步数、调上下文预算完全同一条路径，且会写进演化史留痕。

### 3.4 CLI 表面

```bash
openthree -fast "把这个 typo 修了"          # = --time-budget 120 的糖
openthree --time-budget 60 "查一下这个报错"   # 显式、锁定
openthree "重构这个模块"                      # 与今天完全一样（预算 0）
openthree -fast -i                          # 交互模式里每一问各有 120 s
openthree -fast --auto 3 "…"                # 允许，但提示「每轮 120 s，最多 3 轮」
```

- `-fast` 是 `store_true`（**不能**用 `nargs='?'`：实测 `-fast 修个typo`
  会把任务当成参数吞掉并报错）。
- `-fast` 与 `--time-budget` 同时给：显式秒数优先。
- 横幅多打印一行：`配速：快跑，预算 120 s（工具全开，步数上限不变）` ——
  让人一眼看见「没降级」，只是有期限。

### 3.5 反向约束（这套东西不许做的事）

| 不许 | 理由 |
|---|---|
| 不改工具集 | 拿走工具是削弱能力。旧白名单方案省 4266 tok ≈ 每步 0.19 s，而 A1 修好后这些 token 本来就走缓存 —— 用一个永久的降级去换一个可以修好的 bug |
| 不改步数上限 | 62 次往返是这个任务的真实深度，不是浪费。砍到 12 步会让 17/19 个任务被截断 |
| 不改 `prompts/system-prompts.md` | `-fast` 只影响「这一刻怎么配速」，不改「我是谁」 |
| 不新增磁盘状态 | 除 `limits.json` 多一个键，没有第二种状态文件 |
| 不降可观测 | 反而要加：每步墙钟、剩余预算、退出原因都进 `events/` 与报告 |
| 不静默截断 | 预算用尽就如实说「没做完」，不做成「看起来做完了」 |
| 不影响默认行为 | 不传参数时，`limits.json` / `context.json` 一个字节都不变 |

## 四、和「削减式快」的区别

同样想快，两种做法的差别是本质的：

| | 削减式（把预算改小） | 本方案（把尺子交给模型） |
|---|---|---|
| 快的来源 | 内核少给 | 模型自己省 |
| 工具 | 白名单 9 个 | **35 个全在** |
| 步数 | 硬砍到 12 | **不动（200）** |
| 超时后 | 半句话 + 截断的 `tool_calls` | 一整步用于 `finish`，写清未完部分 |
| 谁在判断「这活该多深」 | 内核里的一个数字 | **模型** |
| 修掉的真问题 | 无 | 缓存 4 %→80 %、重复清单、串行执行、截断提示 |

关键差别在最后一行：削减式方案**不修任何 bug**，它只是把「慢」换成「不完整」。
而 32.7 % 的时间是内核自己浪费掉的 —— 那部分拿回来，是纯赚。

## 六、验收

### 6.1 P0 的 A/B（已执行，结论：通过）

1. 变更前基线：`trace.jsonl` 前 1470 次带 usage 的调用，中位命中 **4.25 %**、均值 5.50 %。
2. 变更后：真实任务（真实 API、真实 Agent 循环）的**稳态步**（第 2 步起）命中
   **82.6 % / 82.8 % / 87.8 % / 95.3 %**，含 `write_plan` 的两次改写仍是 81.8 % / 86.1 %。
3. **通过线**（稳态步命中率中位 ≥ 80 %）：**通过**。
   首调必然低（冷启动无前缀可命中），不计入稳态。
4. 另有 8 条不依赖服务端的回归断言（`tests/test_prompt_prefix_cache.py`）。
5. 每步收益：取 prompt 规模相同的两组（10k–20k tok）比较，高命中中位 **1.97 s**、
   低命中中位 **3.29 s**，即每次往返省约 **1.3 s**。

**顺带证伪了一件事**：把时间戳从 system 开头挪到末尾**不够**。
`tools` 参与缓存、且序列化顺序是 `system → tools → messages`，所以变化段留在
system 里仍会连带废掉一万多 token 的工具 schema。必须挪到 messages 末尾。

**还证伪了一件**：只把「每步都变」的值挪走也不够 —— 计划/记忆/演化史是模型
**自己会写**的，它们留在 system 里，写一次计划同样打断缓存（实测 92 %→27 %）。
所以分层依据不是「谁在变」，而是「**它多久变一次**」。

**另一件被证伪的事**：不能拿 §2.2 的回归系数（0.0444 ms/tok）去推算收益。
真实规模实测，命中缓存每步省约 **1.3 s**，而按回归系数外推会得出 4643 ms —— 高估数倍。
原因是那个系数在「几乎不命中」的数据上拟合，测的是 prompt 变长的边际成本，
与「命中能省多少」不是同一个量。

**这次修复的诚实收益**：每次往返省约 **1.3 s**。中位任务 62 次往返 → 约 **80 s**，
相对中位任务 1205 s 是 **~7 %**。它不是「快很多」，但它是**白拿的**：
不损失任何能力、不改任何默认值、所有模式受益。

## 七、风险与回退

| 风险 | 应对 |
|---|---|
| 服务端并非前缀缓存 → A1 无效 | §6.1 的 A/B 先证伪；不过线就不做 A1 |
| 某些服务端不接受「tool 之后跟 user」 | 处境消息优先用 `user` 角色（最通用的插话方式）；若某服务端拒绝，回退为「静态 system + 动态段留在 system 末尾」，命中率提升减半但仍有收益 |
| 模型无视预算、闷头做完 | 剩余 < 1 步时重复提醒 + 收尾步强制；并把这笔账记进报告（`budget_exhausted`），让人看得见 |
| `-fast` 被误解成「质量下降」 | 横幅与结论都明写「工具全开、步数不变，只是有期限」；结论必须列出未完项 |
| 时间预算与 `--auto` 语义冲突 | 不禁止，只提示「每轮 120 s × N 轮」；实在不适合快跑的活，模型应主动说出来 |

## 八、一页总结

- **慢**：中位任务 62 次往返、模型 819 s；其中 **61.9 % 是模型自己在想**（70 % 是 reasoning）。
- **内核的错只有 32.7 %**：固定开销 9.9 %、未缓存 prompt 22.8 %。后者是纯结构问题
  —— 同一请求重发命中 99.86 %，说明服务端在做，是我们把前缀打碎了。
- **所以**：先修内核（不改内容，只重排消息结构），再把时间做成第六个可自管边界。
- **`-fast` = `--time-budget 120` + 一段「怎么快」的说明**。工具全开、步数不变、
  提示词不减；到点是软着陆，交付诚实的阶段结论。
- **不承诺**「1205 秒的重活压到两分钟」。历史上 19 个任务里只有 1 个能在 120 秒内做完
  —— `-fast` 的意义是给短活一个明确上限，并保证到点的回答是完整的、可信的。
