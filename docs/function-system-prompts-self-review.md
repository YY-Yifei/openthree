# 自评审：function 文件自带的系统提示词（方案）

> 评审对象：`docs/function-system-prompts-proposal.md`（426 行）
> 评审日期：2026-11-02 · 源码基线：`fb42aec`
> 方法：逐条对着源码核，不用记忆代替证据；最后过一遍内核的设计哲学八问
> 结论：**骨架与哲学一致，三处硬伤都在边缘机制上（回溯 / 诊断视图 / 与既有注释的对账），
> 没有一个动到核心假设。修完 P0 即可开工；P1 里有一条要人类拍板。**

---

## 0 结论先说

方案的承重部分是对的，而且有两处比同类设计更干净：

1. **提示词活在 function 文件里**，不新开 `prompts.d/`、不复制 —— 磁盘即真源，没有第二份拷贝；
2. **只收零参**，把「按情境给指导」明确推回给「返回文字的 function」这个既有机制 ——
   没有为了让提示词更聪明而引入条件表达式（那会立刻毁掉缓存前缀）。

缺陷集中在**边缘机制**：它给「一」开了一个新的写入口，却没有把「一」的既有承诺
（可回滚）一起接过去；它要动诊断视图，却没核清诊断视图今天是什么；它新增了一条与
`prompt.py` 里一条既有注释正面冲突的判据，却没对账。

| 级别 | 数量 | 处置 |
|---|---|---|
| **硬伤**（实现出来是错的 / 与代码事实不符） | 3 | 开工前必须改 |
| **站不住**（答辩时会被问倒） | 4 | 开工前定调 |
| **措辞与顺带** | 3 | 改文档 / 实施时顺手 |
| **写对了、且是承重的** | 5 | §5 列出，改的时候别顺手删 |

## 2 硬伤（P0）

### P0-1 「靠 git 追溯」不成立，于是「一」的可回滚性被削弱

**判据**：模型能改自己的地方，必须留下**可读回来**的痕迹。内核在「一」上早就兑现了这条：
`write_system_prompt` 覆写前自动 `snapshot_system_prompt`，配 `list_prompt_versions` /
`read_prompt_version` / `restore_system_prompt` 三件套。这不是装饰，是「自省的前提是可后悔」。

**事实**：方案 §10 把「不写进 `prompts/history/`」的补偿写成「靠 git + recorder 的 sha256 事件追溯」。
但仓库的 `.gitignore` 明写「`.openthree/` 工作区一律不入库」，实测 `git ls-files .openthree/prompts`
为空。于是：

- 模型自己写的 function（`.openthree/functions/*.py`）**没有 git 历史**；
- profile 目录入不入库取决于别人，不能当作承诺；
- recorder 事件里只有 **sha256 + chars + first_line** —— 哈希不能还原内容，
  第 3 行以后是什么，事后查不到。

净效果：**模型可以改自己的 system，事后却看不见改了什么**。这与内核在「一」上的既有承诺
正好相反，而且没人会注意到 —— 因为「有 sha256」看起来已经很严谨。

**改法**（约 10 行，不动 `prompts/history/` 的语义）：
按内容寻址落一份，`reload` 时写 `.openthree/logs/attached-prompts/<sha8>.md`
（append-only、天然去重、可 diff、可恢复），recorder 事件带 `sha8 + file + chars`。
`read_prompts` 的行为不变 —— 它显示当前值，这份文件留着历史值。
`write_function` 的报告里再补一句「本文件覆盖了旧版 `<sha8>`，内容在 `logs/attached-prompts/`」。

顺带一条优化：`AttachedPrompt.sha256` 应复用 `read_source()` 已经读到的源码字符串算，
不必为算哈希二次读盘（`registry._load_file` L311 已经把 source 读进内存了）。

### P0-2 `build_runtime_block` 拼上 attached，会让「兼容壳 == 真正发出去的三段」不可测

**事实**：`build_runtime_block`（`prompt.py:214-236`）拼的是 `static + context + situation`，
**不含「一」**。而 `tests/test_prompt_prefix_cache.py:175-203` 用它守一条不变量：

```python
assert msgs[0]["content"].endswith(static)          # system 以内核常量段结尾
assert build_runtime_block(...) == f"{static}\n\n{context}\n\n{situation}"
```

方案 §7 说「`build_runtime_block` 也拼上它」。照做的话：

- 诊断视图会包含**一个** system 段（attached），却不包含**另一个**（「一」）——
  「谁在 system 里」这件事在诊断视图里没有唯一答案；
- `msgs[0]["content"].endswith(static)` 直接失效（system 变成 `…{static}{attached}`），
  于是那条测试不再是「兼容壳有没有漂移」，而是「有没有按我想的顺序漂移」。

**改法**：让 `build_runtime_block` 改调 `build_system_block(ws, reg, model=...)`，
即诊断视图 = **system + context + situation**，测试相应改成

```python
assert msgs[0]["content"] == build_system_block(ws, registry, model="m")
assert build_runtime_block(...) == f"{system}\n\n{context}\n\n{situation}"
```

这是一次**行为变更**（诊断视图第一次包含「一」），方案里要写明，而不是顺手改测试。
收益是方案 §7 的目标真正达成：`build_messages` 里那段 f-string 拼接消失，
「system 由哪几段组成」只剩 `build_system_block` 一个真源。

### P0-3 与 `prompt._profile_line` 的既有判据正面冲突，方案只绕开

**事实**：`prompt.py:163-177` 的 docstring 写得很硬：

> 这一行说明的是「这些工具从哪来」，不是「我是谁」—— profile 不参与身份，
> 所以它只报来源与数量，**绝不去拼接别人的提示词或记忆**。

方案的整个卖点恰恰是「拼接 profile 里的提示词」（§11 的例子就是把它挂到另一个项目）。
§12 只对账了 `profile-functions-proposal.md` §1（为什么 `system-prompts.md` 不能进 profile），
**没有对账这条写在代码里的注释** —— 而注释比文档更接近真相，因为下一个人读代码时看的是它。

**判据（这条要写进方案）**：那条注释守的是「**身份不变**」，不是「system 里不许有别人的任何字节」。
反证在同文件里：`reg.digest()` 早就把 profile 的工具名与 docstring 首行拼进了 system。
所以真正的不变量是：

> **别人的世界观不进 system；别人的能力说明书可以。**

**改法（两边都要改，缺一不可）**：

- 实施时把 `_profile_line` 的 docstring 改成它真正守的那条（「不拼接别人的**世界观**：
  提示词正文 / 记忆 / 身份；工具与用法说明随能力进入，见 `build_attached_block`」）；
- 方案 §12 点名这条冲突，并说明为什么本方案不推翻它。

只改文档不改注释 → 下一个人会把本方案当 bug 修掉；只改注释不改文档 → 读者以为作者没看见。

## 3 站不住（P1）

### P1-4 双名兼容，与「ancestor 整套移除」的先例相反 —— **已裁定：单名**

方案 §3.1 最初写的是「正名 `__system_prompts__`，同时接受 `__system__prompts` 作别名 + 提示改名」。
名字本身选对了（dunder 判据那一段论证成立），但**别名不该留**：

- 先例：`-profile` 收敛时，ancestor（逐级向上找 `.openthree`）是**整套移除**的，
  理由正是「之前没被用过，不用兼容」；
- 此刻零存量文件 —— 别名今天救不了任何人，将来也救不了，但解释成本永存
  （每份文档、每次 review 都要多写一句「两个名字都行」）。

**判据**：兼容层的价格是「永远要维护两条路径 / 两个名字」，收益是「迁移已存在的存量」。
**存量 = 0 时，价格是无穷大比 0。**

**裁定（2026-11-02，人类）**：单名 `__system_prompts__`，不设别名。方案 §3.1 已按此定稿，
「别名」已从改动面与八问表里一并移除。

**留给自己的判据**：这一条本不该推到人类面前 —— 提案里同时写出两种名字，
等于把「极简」的裁决留给读者。存量 = 0 是当场就能核的事实（全库 `__system_prompts` 零命中），
下次同类问题按判据直接定单名，别把可自证的事做成待拍板项。

### P1-5 §0「代价真的是零」不精确，会被读者当成「不用看 §7」

行为零差异是真的，而且守得住（有逐字节测试）。但：

- 复杂度不是零：四模块新增分支、一个新符号、一条审计判据、四处输出节（别名已按裁定移除）；
- §0 用「**代价真的是零**」起头，读者会跳过 §7 的改动面，以为这是个开关式的零成本特性。

**改法**：措辞收敛为「**你不写，行为一个字节都不变；你写了，才付复杂度**」。
§0 结尾「最好的回应是不写它」也应落到「**先不实现（阶段〇）**」——
「不写」描述的是用法，「不实现」才是决策。

### P1-6 上限缺对照，且与「计划无上限」形成双标

- 单文件 `4000` ≈ `tool_result_limit=4000`，同量级，有对照 ✅；
- 总量 `12000` 无对照，需要给出依据（≈ 3× 单文件，或「实测再调」）；
- 更值得承认的是：`_plan_block` 至今**完全没有上限**（`kernel-analysis-20261013.md` §5 已点出，未修）。
  同一份 system 里，附随提示词有硬上限、计划一个字都不限 —— 两套卫生标准。

**改法**：12000 注明依据；并在常量注释里承认这个不对称、指向 kernel-analysis §5，
顺带把「计划块该有上限」记成一条待办（不塞进本方案，但它已经被点了快一个月）。

### P1-7 测试缺口三条

方案 §8 的清单里守住了最重要的那条（不写时逐字节相等），缺三条：

1. **`reload` 幂等**：`prompts` / `prompt_errors` 必须在 `reload()` 开头清空（方案写了实现，
   没写测试）。连调两次 reload，`len(reg.prompts)` 不能翻倍 —— 这类「列表跨 reload 累积」
   是这类代码最常见的一次性 bug。
2. **`read_prompts` 的附随段长度护栏**：模型自造三份 4000 字符的说明书之后，
   `read_prompts` 一次就能吃掉小半个上下文。应对齐 `_recent_evolution(limit=10)` 的做法：
   只显示前 N 段 / N 字符，完整内容指向 `--print-prompts`。
3. **sha256 复用 `read_source`**（见 P0-1），并测一次「不二次读盘」不必单测，
   但要保证 `AttachedPrompt.sha256` 与文件内容一致。

## 4 措辞与顺带（P2）

- **审计输出报「形态」比三个布尔好**：`has_prompts` + `prompt_form`（`str` / `list` / `callable` /
  非法）+ `prompt_chars`，比 `prompt_callable` 布尔少一项、信息更多。
- **§6 表格的行号会漂**：①「函数名 + 行号（截至 `fb42aec`）」比裸行号耐用；② `builtins.py`
  的行号本方案全部没核（本轮只核了 `registry` / `prompt` / `tool`），实施前要重新对一遍。
- **§10 应补一条「不做内容审查」**：想加护栏的人第一个会想到「禁止出现『你是』『你的名字』」，
  而那正是硬编码智能。明确写一句拒绝，比留白好 —— 留白会被后来者填上。

## 5 写对了、且是承重的（改的时候别顺手删）

1. **三种形态只收 str / list[str] / 零参可调用**，并把 `kernel` 排除（离线 CLI 下内核未铺好）——
   判据准确，理由给了双重（语义 + 实现）。
2. **求值放 `reload`**，并把它论证成「`STATIC_TEMPLATE` 注释里那条不变量」而不是「省事」。
   实测支撑：`agent.py` 从不 reload，一条 function 文件的生命周期很清晰。
3. **§4.1 那句「这不是技术上的强制降权」** —— 承认「它和『一』都躺在 system 里，分量相同」。
   方案里最诚实的一句，删了它整篇就变成吹牛。
4. **§4.3 的上限理由**：「这是唯一能零成本污染 system 的入口」。判断对，且它解释了为什么
   别的地方没设上限（别的地方进 system 的量都是机械派生、有天然上限）。
5. **§10「不做开关」**：`不写那个符号` 就是关，且是代码路径根本不进，比运行时跳过干净。
   这条与「极简」同向，也是最可能被推翻的一条 —— 所以它需要 P1-5 的措辞修正来撑住。

## 6 设计哲学八问

| # | 问题 | 结论 | 依据 |
|---|---|---|---|
| 1 | **道**：有没有把判断写进代码 / 常量 / 关键词？ | ✅ | 方案只搬运，不判断。前提：把「不做内容审查」写进 §10（P2） |
| 2 | **一**：可写 **且可回滚**？ | ⚠️ **半通** | 可写 ✅；可回滚 ❌ —— 这是全篇唯一的哲学级缺陷（P0-1） |
| 3 | **二**：磁盘即真源、没有第二份拷贝？ | ✅ | 提示词活在 function 文件里，不新开目录、不复制 |
| 4 | **三**：有没有预设循环？ | ✅ | 只给说明书，不规定「先做什么再做什么」 |
| 5 | **万物**：让模型更容易自造，还是更难？ | ⚠️ | 能力面扩张 ✅；**自省面缩水** ❌（与 P0-1 同源） |
| 6 | **极简**：多一条要维护的路径吗？ | ⚠️ | 别名已按裁定移除；四模块分支不可避免，但 §0 的措辞让人以为不用付（P1-5） |
| 7 | **成本**：system 的字节从「随文件变」变成「随每步变」了吗？ | ✅ | 随 reload 变，与 static 同频，归位正确。**但论证该换成变化频率**：方案给的理由是「语义位置正好」，真正的理由是「与 static 同频」；只按语义论证，下一个人会问「那为什么不放 context block」 |
| 8 | **诚实**：读数与措辞站得住吗？ | ⚠️ | 两处与事实不符（§10 的 git 追溯 / §0 的代价为零），而文档自己在 §4.1 要求「最后一句要诚实」—— 属于自我不达标 |

**八问里五条通过、三条打折，而三条打折全部指向同一件事**：这个方案给「一」开了一个新入口，
却只用**措辞**（「不是你的身份」）来约束它，没有用**机制**（可回溯的痕迹）来接住它。
措辞管得住今天的读者，管不住明天的搜索。

## 7 总评

**骨架与内核哲学一致，不必重做。** 缺陷全部落在**边缘机制**这一层 —— 回溯、诊断视图的一致性、
与既有注释的对账 —— 没有一条动到核心假设（三种形态 / 只收零参 / reload 求值 / 近者优先 /
无开关 / 无覆盖）。修完 P0 三处（约 30 行代码 + 3 句注释 + 2 处测试）即可开工。

**P1-4 已裁定为单名**，接口定稿；需要人类拍板的项已清零，其余缺陷都是我能自己修的。

开工前的判据一句话：**如果实施完，模型改了自己的 system 之后，还能在磁盘上读到
「改之前是什么」——这个方案就成立了；读不到，就还差 P0-1 那 10 行。**

## 8 实施之后的两轮自评审（2026-11-02）

方案评审管得住「设计错没错」，管不住「代码有没有照设计做」。实施完又过了两轮：
第一轮读实现、第二轮拿八问与文档断言去核。**第 3 条 P0-1 的判断是对的**（痕迹确实
必须落盘），但第一轮的七处缺陷没有一处是设计错，全部是「一份判据写了两遍」或
「平台差异把一个承诺变成假的」。

### 第一轮（实现级）

| # | 缺陷 | 为什么漏了 | 判据 → 改法 |
|---|---|---|---|
| 1 | `_persist_prompts` 用 `write_text`：Windows 上落成 CRLF，**文件名的 sha8 ≠ 文件内容** | 测试用 `read_text` 断言，而它会把 CRLF 归一化成 `\n` —— 断言与被测对象被同一个转换掩盖 | 「内容寻址」的字面意思：`sha256(read_bytes()) == 文件名` → 改 `write_bytes`，断言改按字节 |
| 2 | `register_function` 硬拒纯提示词文件 | §6 数了四条判据（注册器 / 审计 / `write_function` / CLI），漏了登记通道 | 五条判据必须同一答案 → 放行，并明说「这次登记带来了什么」 |
| 3 | `verify_tool` 对纯提示词文件只回「没有任何可注册的公开函数」 | `_VERIFY_SCRIPT` 只验工具，从没看过这个符号 | 验收 = 上岗前证明它能跑 → 子进程同样求值，报段数 / 字符 / 首行 / 错误 |
| 4 | CLI `--print-prompts` 在没写提示词的文件上退化为 argparse「未识别的参数」exit 2；求值失败被吞掉 → 误诊成「没有公开函数」 | 只在「有提示词」时才认这个选项 | 查询永远该回答（可以是空）→ 解析前无条件先认；错误照原样打到 stderr、退 1 |
| 5 | `--help` 在纯提示词文件上把正文当帮助打印 | 无工具分支只写了「有提示词就打正文」 | `--help` 问的是「怎么用」→ 单独回答一句 |
| 6 | 截断后 `len(text) > 4000` | 上限只作用在正文上，忘了截断说明也是要进 system 的字 | 常量说的是「进 system 的上限」→ 说明计入上限 |
| 7 | 审计里硬编码「4000」；`prompt_kind` 是死字段；`original_chars` 没人读 | — | 一个数只能有一份 → 用常量；死字段删掉；截断过的在摘要里写出原文长度 |

第 6、7 条是「文档里的数字与代码里的数字不是同一件事」这一类：它们单独看都很小，
但审计提示说「单文件上限 4000」而实际进了 4030 字，下一个读它的人就会以为审计在说谎。

### 第二轮（哲学级 + 事实级）

- **八问复走**：①道 ✅（实现里没有一处按内容分支）②一 ✅（**痕迹按字节同名于内容**，
  这才真的可回滚）③二 ✅（没有第二份拷贝：`Registry.prompts` 是 reload 期的求值结果，
  不是副本）④三 ✅ ⑤万物 ✅（`read_prompts` / `list_functions` / `--print-prompts` 三处
  都能看见它）⑥极简 ✅（无开关、无别名、无配置项）⑦成本 ✅ **且有测试钉住**
  （新增 A6：改文件不 reload，system 不许变）⑧诚实 ⚠️→✅（见下两条）。
- **事实级：`read_prompts` 里那句「与「系统提示词」冲突时以它为准」** —— 「它」指谁，
  两种读法正好相反，而 `ATTACHED_PROMPT_TEMPLATE` 里写的是「以「一」为准」。同一件事
  在系统提示与工具输出里能读出两个意思 → 改成明写「以「系统提示词」为准」。
- **README 教了一个会盖掉自己的写法**：同一个代码块里既 `__system_prompts__ = "…"`
  又 `def __system_prompts__()` —— 照抄就是后者盖前者。改成一段正文说明三种形态。
- **README「超了会如实报告」不精确**：单文件超限是截断（写在正文里），只有合计超限
  才进 `prompt_errors`。措辞改成分别说清。
- **P1-7 三条缺口的处置**：①`reload` 幂等 —— 测试补了 `len(prompts) == 1`；
  ②`read_prompts` 长度护栏 —— **裁定不做**：`tool_result_limit` 已经是那道护栏，超了会
  落盘并指出路径，再加一层分页只会让「看到的就是全部」变复杂（不写就是零）；
  ③sha 与内容一致 —— 第一条的修复就是它。
