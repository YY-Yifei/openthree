# 自评审：`docs/a2a-real-cancel-plan.md`

> 评审对象：A2A「真实停止」方案 · 2026-11-17
> 方法：先自己反驳一遍，再对着源码逐条核事实，最后把「与既有判据冲突」的地方点名

## 0. 结论

骨架与哲学一致：**中断点长在 ReAct 循环里（三），取消信号长在频道层（二），内核不替任何人判断「该不该停」**。
但第一稿有四处会写错，评审后已改进方案：

- **第一层（核心假设，P0）**：`CancelToken.request()` 里无条件 `abort_all()` —— 全局注册表不认归属，
  会把**别的运行**在飞的 socket 一起关掉（最典型：`-i` 控制台在跑、A2A 收到一个排队任务的 cancel）。
  已改成「socket 记住它的 owner 令牌，只关该令牌自己的」。
- **第二层（机制，P0）**：`_rpc_cancel` 要等 `cancel_grace`，而现有代码是「持锁查状态 → 锁外 `_finish`」
  （`a2a.py:1790-1795`）。若把等待挪进 `with self._tasks.lock:`，桥线程的 `send_text` 永远拿不到那把锁，
  就是**取消把自己等死**。方案已写明「锁里只取 Event，锁外等」。
- **第三层（漏改，P0）**：`Cancelled` 会被两处 `except Exception` 吞掉 —— `agent._execute`（`agent.py:1031`）
  会把它变一条 tool 错误字符串，ReAct 继续跑到下一步；`runtime._run_round`（`runtime.py:439`）会把它记成
  `status="error"`。两处都必须先认领 `Cancelled`。
- **第四层（措辞，P1）**：§3 那张上界表原本只在方案里。它必须原样进 README、`a2a.py` 模块限制段与
  `tasks/cancel` 的响应文案 —— 否则「真实停止」会变成一句新的谎话。

**它推翻了既有判据，这一点必须说清**：`docs/a2a-channel-proposal.md` §6.1、`README.md:794-795`、
`a2a.py:26` 三处都白纸黑字写着「cancel 不停手，因为 ReAct 没有中断点」。本方案的前提正是**造出那个中断点**。
不是「旧文档写错了」，而是**旧文档的前提被消掉了** —— 因此它们必须跟着改，否则下一个人会把本方案当 bug 修掉（§4）。

## 1. 八问

1. **道（无硬编码智能）**：`cancel.py` 只做三件事 —— 记「已被要求停止」、通知注册过的中断器、让等待可被唤醒。
   它**不判断该不该停**（那是调用方的决定），也不判断「停在哪一步更合适」（那是模型与用户的）。
   `if token.requested:` 这类分支判的是**外部事实**（有人按了停止），不是内容分类。**通过。**
2. **一（可写 · 可回滚）**：不碰 system 提示词、不碰 `prompts/`。「能不能被停」是运行期行为，不是世界观。
   **通过。**
3. **二（磁盘即真源）**：令牌是**内存对象**，不落盘 —— 这里要辩护一句：磁盘即真源管的是「配置 / 能力 / 身份」
   这类**持久**状态；取消是**瞬时控制信号**（写盘再读会让「上一轮留下的 cancel 文件把下一次启动的第一轮直接杀掉」，
   那才是真的错）。同类先例：`KERNEL.state`、`_run_lock`、`IncomingMessage.attachments` 都是内存。
   **通过，但判据要写进 `cancel.py` 的 docstring。**
4. **三（循环不预设）**：检查点只说「该不该继续」，不说「先做什么再做什么」。取消时模型已经产出的思考仍入档。
   **通过。**
5. **万物（自造）**：本方案让「自造 function 如何配合停止」有了一个公开把手（`cancel.current()`），
   工具作者可以自己轮询 —— 比现在「完全没门」是进步。**通过。**
6. **极简**：新增 1 个模块 + 1 个字段 + 6 个检查点 + 3 处终态。能减吗？「检查点 #4（`_execute` 前）」与 #2 冗余，
   但它只花一行、且覆盖 `finish` 之后的其他路径 —— 留。**socket 中断（§4.3）不能减**：没有它，最坏停止延迟是 600s×4，
   那就不叫停止。**通过。**
7. **成本**：system 字节零变化；每步多一次 `Event.is_set()`（纳秒级）；每请求多 2 次 set 增删。
   **不引入「随每步增长」的东西。通过。**
8. **诚实**：这是本方案最脆弱的一处。第一稿有三句话过强，已改：
   ①「真实停止」→ 明确为「不再开始」，并给上界表；
   ②「立刻能接新消息」→ 加限定「前提是 `rt.run()` 真的返回了」；
   ③「停在第 N 步」→ 只在**确认停下**时才这么说，否则说「已请求，未确认」。
   仍然做不到的（自造 function 死循环）已写进 §8，**不假装能做到**。**通过，留 2 条 P1 实测项。**

## 5. 待确认（要人拍板，不替人定）

1. **`cancel_grace` 的默认值**：`0`（立刻回 `canceled`，永不确认）还是 `2s`（多等两秒换一句「真的停在第 N 步」）。
   方案暂定 `2s`，理由写在 §4.6；但这是「响应速度 vs 诚实度」的取舍，**该由人定**。
2. **要不要阶段 2**（`run_shell` 挂 killer）：不做的话，A2A 收到一个 `build` / `pytest` / `ocr review` 任务后取消
   要等它自己跑完（最长 3600s）。做了只改 `builtins.py` 约 20 行。
3. **要不要阶段 3**（`--cancel-hard-grace` → `os._exit`）：**这是「停机器」不是「停一轮」**。我倾向不做，
   但如果连自造 function 死循环也必须能停，它是唯一的路。
4. **`status="canceled"` 还是复用 `"interrupted"`**：方案选前者（A2A 的 `canceled` 与 Ctrl-C 的 `interrupted`
   语义不同，报告里应该能分开）；代价是 `recorder._TERMINAL_STATUSES` 加一项、两处断链加一项。
5. **`tasks/cancel` 的 artifact 是否允许在 `completed` 之后被 `canceled` 覆盖**：方案的选择是**不覆盖**
   （答完了就是答完了），只有 `canceled → canceled` 走同状态。这一条要不要放宽，需人定。

## 6. 我不同意自己的两处（保留争论）

- **「socket 注册表用全局」这件事我不太满意**。它依赖「进程内至多一个在飞 ReAct」这条隐含前提 ——
  虽然今天由 `_run_lock` 保证，但那是 `bridge.py` 的实现细节，不是 `llm.py` 的契约。更干净的写法是把
  owner 令牌随 `post_json` 传下去（`post_json(..., owner=None)`），代价是签名变化、十几个 stub 要跟着改。
  **我选「全局 + owner 标记」**：签名不变的价值（既有测试零改动）大于「`llm.py` 不依赖全局状态」的纯粹性。
  这条要在 `cancel.py` 的模块 docstring 里明写成**前提**，并注明「将来若并发跑两个 ReAct，第一个要改的就是它」。
- **「取消优先于答完」我不确定为真**。方案选了「答完了就是答完了」：`_rpc_cancel` 到达时若状态已是 `completed`，
  原样返回、不改写成 `canceled`。另一种观点是「调用方说停就停，哪怕它刚答完」。我选前者，因为**状态要描述事实**
  （它确实答完了），而「我想要它停」是调用方的意愿，不该覆写事实。这条留给人。

## 7. 补充评审（§4.8：已经卡死的命令）

**结论**：这一节补的是前六节最大的口子。前三节都假设「线程还能走到下一个检查点」，
而一条卡死的命令恰好让这个假设失效 —— 缺陷落在**核心假设**层，不是措辞。

### 实测推翻了我自己的第一稿

- 第一稿：`run_shell` 改成 0.2s 分片轮询（§4.8.3 初版）。
- 第二次实测（`.openthree/tmp/probe_kill_wakes.py`）：另一线程 `proc.kill()` 能让阻塞中的
  `communicate(timeout=30)` 在 **1.000s** 返回（kill 自身 0.0000s，已输出的 `start` 完整保留）。
- 于是改成**不轮询**：`communicate` 那行原样不动，只挂 killer。25 行 vs 40 行，
  且**零新增热路径**（`run_shell` 是内核最热的工具之一）。
- 轮询降为备选（`probe_communicate.py` 证明它同样不丢输出：9 片 / 1.75s / 三段完整），
  只在「某平台 kill 唤不醒 communicate」时启用。
- 顺带实测轮询对快命令的开销：`slices=1 / 0.063s` vs 一次等到底 `0.047s`（差 16ms，噪声级）。

### 新增硬伤

| 级别 | 硬伤 | 判据 | 改法（已落进方案） |
|---|---|---|---|
| P0-5 | killer 同步跑在取消请求里 | `_kill_tree` 的 `taskkill` 自带 `timeout=10`（`builtins.py:536`）⇒ `tasks/cancel` 的 HTTP 响应最多晚 10 秒，正好违背「立刻」 | `request()` 只置事件 + 起 daemon 线程；killer 先 `proc.kill()`（0.0000s）再后台清树 |
| P1-7 | 只杀直接子进程 ⇒ 「取消了但命令还在后台跑」 | Windows 上 `proc.kill()` 只死 `cmd.exe`；孙进程（`pytest` / `node`）继续写文件，与下一轮并发 | killer 第二段 `taskkill /F /T`；返回前 2s grace + join，清干净没有如实写进工具返回值 |

### 立场修正

- **阶段 3（硬退出）从「可选 / 倾向不做」改为「A2A 常驻下必须」**。理由链：桥只有一条
  工作线程（`bridge.py:138-148`）→ 一条无上界的工具扣住它 → 队列里的新消息**永远排不上**
  → 取消再准也换不来「能接新活」。排序是「服务可用 > 进程不重启」。

### 我不同意自己的一处（保留争论）

- killer 唤醒依赖「子进程死了 ⇒ 管道 EOF ⇒ `communicate` 返回」这条链。实测成立

### 我接受「默认关」，并说清我错在哪
